1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
================================================================================
Modern enterprise networks generate massive volumes of continuous network telemetry
(gigabytes per minute, millions of flow packets). Traditional Security Information 
and Event Management (SIEM) systems and relational databases (RDBMS) fail under this 
scale due to single-node memory ceilings, rigid schemas, and write lock bottlenecks.

This project delivers a production-grade, distributed cyber threat intelligence 
platform capable of:
  1. Ingesting and storing massive network flow datasets across distributed NoSQL
     (MongoDB Atlas Sharded) and distributed cold storage (Apache Hadoop HDFS).
  2. Executing distributed cleansing, schema normalization, and feature scaling 
     using Apache Spark 3.5.5 in-memory Catalyst processing.
  3. Training distributed multi-class machine learning classifiers (PySpark MLlib 
     Random Forest & Decision Tree) to classify intrusions into 5 classes:
     PortScan, DDoS, BENIGN, BruteForce, and Botnet.
  4. Computing composite 0-100 IP Reputation & Risk Scores based on attack frequency, 
     severity multiplier, and target blast radius.
  5. Providing an enterprise Security Operations Center (SOC) Console with 
     zero emojis, global geospatial threat maps, automated incident response, 
     and MITRE ATT&CK mitigation rule generation.

2. THE 5 V's OF BIG DATA IN THIS PROJECT
================================================================================
1. VOLUME:
   Raw network capture logs (e.g., CICIDS2017) contain millions of records and tens
   of gigabytes of flow telemetry. Handled via HDFS 128MB block splits and MongoDB 
   horizontal sharding across cluster nodes.

2. VELOCITY:
   Ingress network telemetry arrives at millisecond rates. Apache Spark's in-memory 
   processing processes micro-batches in ~1.8 ms per flow, eliminating slow disk I/O.

3. VARIETY:
   Telemetry spans structured CSVs, semi-structured JSON documents, network PCAP 
   metadata, protocol metrics (TCP, UDP, ICMP), and unstructured threat indicators.
   MongoDB's dynamic BSON document model accommodates schema variations seamlessly.

4. VERACITY:
   Network traffic contains high noise, malformed headers, duplicate records, and 
   null packets. PySpark ETL eliminates duplicate sessions, normalizes timestamps, 
   and standardizes feature variances via StandardScaler.

5. VALUE:
   Raw packet bytes are transformed into actionable threat intelligence: automated 
   MITRE ATT&CK technique mapping, firewall ACL generation, and 0-100 IP risk scores.

3. ARCHITECTURAL TOPOLOGY (3-NODE DISTRIBUTED CLUSTER)
================================================================================
The platform is designed around an enterprise 3-Node Distributed Cluster topology:

                         +----------------------------------------+
                         |              MASTER NODE               |
                         +----------------------------------------+
                         |  - MongoDB Router (mongos :27017)      |
                         |  - Spark Master (spark://master:7077)  |
                         |  - Hadoop NameNode (hdfs://master:9000)|
                         |  - YARN ResourceManager (:8032)        |
                         |  - Streamlit SOC Console (:8501)       |
                         +-------------------+--------------------+
                                             |
                        +--------------------+--------------------+
                        |                                         |
         +--------------+---------------+          +--------------+---------------+
         |        WORKER NODE 1         |          |        WORKER NODE 2         |
         +------------------------------+          +------------------------------+
         |  - MongoDB Shard 1 (:27018)  |          |  - MongoDB Shard 2 (:27019)  |
         |  - Hadoop DataNode 1 (:9866) |          |  - Hadoop DataNode 2 (:9866) |
         |  - Spark Worker 1 (:7078)    |          |  - Spark Worker 2 (:7079)    |
         |  - Storage: /data/shard1     |          |  - Storage: /data/shard2     |
         +------------------------------+          +------------------------------+

Node Responsibilities:
  - MASTER NODE: Manages metadata, job scheduling, distributed query routing, 
    and web dashboard presentation.
  - WORKER NODES: Store raw data blocks (HDFS DataNodes), store partitioned 
    collections (MongoDB Shards), and execute in-memory transformations (Spark Workers).

5. TECHNOLOGIES USED & BIG DATA RATIONALE (WHY EACH TECH WAS CHOSEN)
================================================================================

1. APACHE SPARK & PYSPARK MLLIB (v3.5.5):
   - Role: Distributed in-memory data processing, ETL, and machine learning.
   - Why Chosen over Pandas / Scikit-Learn:
     * Pandas and Scikit-Learn execute in a single Python process and require all 
       data to fit into physical RAM. They crash with Out-Of-Memory (OOM) errors 
       on multi-gigabyte log datasets.
     * Apache Spark abstracts data into Resilient Distributed Datasets (RDDs) and 
       DataFrames partitioned across cluster worker nodes.
     * Spark's Catalyst Optimizer optimizes query plans (predicate pushdown, column 
       pruning), executing transformations in memory at 10x-100x the speed of Hadoop MapReduce.

2. MONGODB ATLAS & SHARDED CLUSTER (v7.0):
   - Role: High-throughput document store for raw logs, IP reputations, and threat metrics.
   - Why Chosen over Relational RDBMS (MySQL / PostgreSQL):
     * Network security telemetry arrives at high velocity with varying attributes 
       (HTTP headers vs DNS payloads vs ICMP echo requests). RDBMS requires rigid 
       schemas and costly table alterations.
     * MongoDB provides dynamic schema flexibility (BSON) and horizontal sharding.
       Hashed shard keys distribute read/write traffic across multiple replica sets, 
       eliminating write bottlenecks.

3. APACHE HADOOP HDFS (v3.3):
   - Role: Distributed, fault-tolerant cold storage for raw log files.
   - Why Chosen:
     * Provides commodity hardware distributed storage with a 128 MB block size 
       and 3x replication factor. If a DataNode fails, data remains available.
     * Functions as the centralized data lake from which Spark reads raw batch logs.

4. STREAMLIT & PLOTLY:
   - Role: Interactive web-based SOC analyst presentation console.
   - Why Chosen:
     * Enables rapid, reactive dashboard rendering with Python.
     * Plotly provides hardware-accelerated, interactive WebGL charts (donuts, 
       scatter plots, radar benchmarks, Carto-Dark global geospatial maps).

5. PARQUET COLUMNAR FILE FORMAT:
   - Role: Intermediate storage for cleaned logs and feature vectors.
   - Why Chosen over CSV:
     * Parquet is a columnar storage format with Snappy compression.
     * Reduces storage footprint by up to 75% compared to raw CSV.
     * Allows Spark to read only required feature columns, significantly speeding up I/O.

6. MACHINE LEARNING & MATHEMATICAL FORMULATION
================================================================================

A. DISTRIBUTED PYSPARK MLLIB CLASSIFICATION:
   - Feature Vector (8 dimensions):
       1. flow_duration        (Total session microsecond duration)
       2. packet_count         (Total packet exchanges)
       3. packet_length        (Mean packet byte size)
       4. total_bytes          (Total bandwidth consumed)
       5. hour                 (0-23 temporal feature)
       6. day_of_week          (1-7 day index)
       7. protocol_index       (Encoded TCP=0, UDP=1, ICMP=2)
       8. severity_index       (Encoded Low=0, Medium=1, High=2, Critical=3)

   - Preprocessing Pipeline:
       StringIndexer -> VectorAssembler -> StandardScaler -> Model Classifier

   - Benchmark Performance:
       * Decision Tree Classifier: Accuracy = 98.59%, F1 = 0.9859, Train Time = 4.11s
       * Random Forest Classifier: Accuracy = 99.23%, F1 = 0.9923, Train Time = 3.01s
       * Rationale: Random Forest constructs 20 uncorrelated decision trees with random 
         feature subsets, reducing variance and eliminating overfitting on noisy flows.

B. DYNAMIC 0-100 IP REPUTATION SCORING FORMULA:
   For every unique Source IP in the platform, a composite risk score is calculated:

     Risk Score = min( 100, Frequency_Score + Severity_Multiplier + Dispersion_Score )

   Where:
     1. Frequency Score (0 to 40 points):
          min( 40, Attack_Count * 4 )
     2. Severity Multiplier (0 to 40 points):
          DDoS = 40 pts | Botnet = 30 pts | BruteForce = 25 pts | PortScan = 15 pts | BENIGN = 0 pts
     3. Destination Blast Radius / Dispersion Score (0 to 20 points):
          min( 20, Unique_Destinations * 4 )

   Threat Tiers & Automated SOC Policy Mapping:
     - 76 to 100 (Critical Tier): BGP Flowspec Null-Route & Hard Perimeter Isolation
     - 51 to 75  (High Tier)    : Host Credential Quarantine & Active Session Drop
     - 26 to 50  (Medium Tier)  : Rate-Limit & TCP SYN Cookie Challenge
     - 0 to 25   (Low Tier)     : Standard Network Monitoring & Normal Routing

9. VIVA & EXAMINER Q&A CHEATSHEET (COMMON BDS QUESTIONS & ANSWERS)
================================================================================

Q1: Why did you use Apache Spark instead of Python Pandas?
A1: Pandas executes within a single Python interpreter process and requires the entire 
    dataset to fit into single-machine RAM. If the dataset exceeds RAM (e.g., 50 GB log file), 
    Pandas crashes with an Out-of-Memory (OOM) error. Apache Spark partitions data into 
    Resilient Distributed Datasets (RDDs) across Worker 1 and Worker 2, performing 
    distributed in-memory computation in parallel.

Q2: Why use MongoDB instead of MySQL or PostgreSQL?
A2: Network flow telemetry arrives at high velocity with varying packet attributes. 
    RDBMS requires strict schema enforcement and locks tables during heavy bulk writes. 
    MongoDB's document-oriented BSON model allows flexible semi-structured storage, and 
    horizontal sharding distributes write loads across multiple shards using a shard key.

Q3: How does PySpark train a Random Forest across multiple worker nodes?
A3: PySpark MLlib uses parallel tree construction. For each node split, the Spark driver 
    broadcasts candidate split bins, and worker nodes compute feature histograms and 
    Gini impurities on their local data partitions in parallel. The results are aggregated 
    at the driver to select the optimal split, without moving all raw data to a single node.

Q4: What is the purpose of HDFS when MongoDB is already present?
A4: HDFS serves as cold, immutable distributed raw storage (Data Lake) for multi-gigabyte 
    PCAP files and raw batch logs with 128MB block splits and 3x fault-tolerant replication. 
    MongoDB serves as the queryable hot storage layer for real-time lookups, aggregated metrics, 
    and fast dashboard queries.

Q5: Why did your Random Forest model achieve 99.23% accuracy compared to Decision Trees?
A5: A single Decision Tree is prone to high variance and overfitting on noisy network packet 
    variations. Random Forest builds an ensemble of 20 decision trees, each trained on a random 
    bootstrap sample of data and a random subset of features. Averaging predictions across 
    uncorrelated trees cancels out individual errors, yielding higher generalized accuracy.

Q6: How does your system handle node failures?
A6: Hadoop HDFS uses a 3x replication factor; if DataNode 1 fails, DataNode 2 serves the block. 
    Spark RDDs use lineage graphs to recompute lost partitions on surviving workers. 
    MongoDB replica sets elect a new primary node within seconds via Raft-like consensus.
